## 2. Tux Paint と他アプリの観察事実

### 2.1 Tux Paint【事実】
- 対象は子供向けの無料描画ソフトで、年齢は約 3〜12 歳（公式サイト）。GPL、広告なし、オフラインで動作。Windows/macOS/Linux/Android など。
- ツール: Paint（ブラシ。ブラシごとに音、大きいほど低音）、Stamp、Lines（ドラッグ中にゴム紐の線と角度を表示。離すと「sproing」音）、Shapes、Text、Label、Fill（べた塗り・ブラシ・グラデーション数種）、Magic（効果）、Eraser、Undo/Redo、New、Open、Save、Print。
- Stamp: カーソルに追従する輪郭でプレビューし、クリックで押す。大きさは右下の三角バー、反転・ミラーは右下のボタン。回転は切り替えで有効にし、「移動して角度を決め、もう一度クリックして確定」の二段階。カテゴリは左右の矢印で切り替え。一部は色を変えられる。スタンプは効果音と音声説明を持つ。
- Shapes: 「押して引いて大きさ→離して回して角度→クリックで確定」。中心から描く／角から描くの切り替えあり。
- Text は確定すると絵の一部になり、後から動かせない。Label は絵の上に浮いたまま編集でき、「適用」で確定してラスタ化される。つまり Tux Paint は「押したら絵に焼き付く」方式が基本で、再編集可能なオブジェクトは Label だけ。
- Eraser: Paint と同様に動かし、消した所は元の背景（単色・スターター・テンプレート）が出る。四角・丸・ぼかし円など複数形状・サイズ。
- Fill: 1 クリックで連続領域を塗る（solid）。
- 保存: Save はファイル名を聞かず、シャッター音。保存済みの絵は「上書き／新規」を選ばせる。形式は PNG（YYYYMMDDhhmmss.png）。Open は保存した絵のサムネイル一覧（開く・消す（確認あり）・書き出し・スライド・テンプレート化）。
- 子供向けの工夫: 大きなボタン（buttonsize 24〜192px）、効果音、確認ダイアログ（New・Quit・Open 時の未保存・消去）、簡易化オプション（simpleshapes=図形の回転工程を省く、nostampcontrols=反転・拡大縮小を隠す、nostamprotation、nolabel、noprint、nosave、noquit、complexity=novice、mouse-accessibility=ドラッグの代わりに「クリック・移動・クリック」）。
- Undo/Redo は複数回可能（上限回数はドキュメントに記載なし【未確認】）。
- ライセンス: プログラムは GPL。スタンプ素材は一つの許諾ではなく、パブリックドメイン、CC BY、CC BY-SA、GPL、GFDL などが混在（検索要約。CONTRIBUTORS は本文未読）。公式 HOWTO は「GPL と互換の画像」を求めている。【示唆】コード・素材・アイコン・効果音は流用しない。本調査は仕様の観察のみに使用し、まなびのにわ側は自前で作る。

### 2.2 Kid Pix【事実（二次資料、出典不足の注記あり）】
- 作者が 3 歳の息子のために作った。1989 年に Mac 向けの無料版、1991 年に Broderbund が商用化。道具は鉛筆・線・バケツ・四角・丸、Wacky Brush、Mixer、Rubber Stamps、爆発する消しゴム（ダイナマイト）など。文字スタンプは文字名を読み上げる。
- 「Undo Guy」はキャラクターが取り消しボタンを兼ね、押すと様々な声で面白いことを言う。Deluxe 3D 以降は複数回の取り消し・やり直しが可能で、以前は 1 回のみ。
- 【示唆】失敗の取り消しをキャラクター化し、「失敗しても大丈夫」を楽しく見せる工夫は幼児向けに有効そうだが、効果は検証されていない。本アプリでは固有キャラの模倣を避け、自前の表現にする。

### 2.3 幼児（2〜5 歳）の描画・タッチ操作【事実】
- Kirkorian ほか（2019）: 2〜5 歳 73 名と成人 24 名が図形を模写（紙とマーカー／タブレットとスタイラス／タブレットと指）。子供の「採点可能な絵」の割合は指 66%・マーカー 61%・スタイラス 59%。指の優位は主に低年齢の男児で、年齢とともに縮小。絵の品質（高評価の割合）は媒体間で有意差なし。自由に描く時は約 79% がタブレットを選び、その多くが指よりスタイラスを選んだ。著者は、標本が便宜的で課題が単純な模写なので自由画に一般化できないと述べている。
- Nácher ほか（2015、要旨のみ）: 2〜3 歳でも、タップ・ドラッグ以外に 1 本指の回転や 2 本指の拡大縮小を基本ジェスチャと同程度にできた。一方、ダブルタップ・長押し・縮小・2 本指回転には認知・精度の問題があった。
- Sesame Workshop（2012）: タップが最も直感的、ピンチとフリックは難しい。タブレットを横向きに持ち、手首を下端に置くので、下端のボタンは誤タップの原因になる。【二次報道による補足、原文未確認】タップは指を置いた時点で反応させる／5 歳未満はドラッグ&ドロップが難しく「タップして、タップする」方式が有効／描く時に指が浮きやすいので途中までの結果も有効にする。
- Ahearne ほか（2016、親の報告・82 名）: スワイプの月齢中央値 24 か月。観察でなく親の申告。
- 【示唆】研究は模写課題や小規模調査が中心。「スタンプが好まれる」を直接示す一次資料は見つからなかった【未確認】。スタンプ偏重は仮説として扱い、観察メモ（保護者画面）で検証する。

## 4. ラスタとオブジェクトの関係（設計案と比較）

### 4.1 案
- **案 A 「焼き付け」（Tux Paint 型）**: 全部ラスタ 1 枚。はんこ・図形は確定した瞬間に絵になり、後から動かせない。消しゴム・塗りつぶしは常に同じ対象。
- **案 B 「ラスタ層＋オブジェクト層の 2 層」**: ペン・塗り・消しゴムは下のラスタ層、はんこ・図形は上のオブジェクト層（常に最前面）。
- **案 C 「確定まで浮かせる（焼き付け式の拡張）」**: 置いたオブジェクトは「浮いた状態」で選択・移動・拡大・回転・削除できる。ペン・塗り・消しゴム・別のオブジェクト操作を始めるとき、浮いているものをまとめてラスタ層へ焼き付ける。浮かせる数は 1 個（幼児）〜数個（小学生）に制限。
- **案 D 「全部オブジェクト」**: 線もパスのオブジェクトにし、描いた順の積み重ねを保つ。いつまでも再編集できる。

### 4.2 一貫性の比較

| 観点 | A | B | C | D |
|---|---|---|---|---|
| 重なり（後から描いたものが上） | 一貫 | 破綻（線を引いてもはんこの下に入らない） | 一貫（焼き付けで順序が確定） | 一貫 |
| 消しゴム | 見た目通り何でも消える | はんこが消せない。専用操作が必要 | 浮いている間は選択削除、焼き付け後は何でも消える。一貫性は A に近い | 手法が不明（線消し／部分消し）。実装が重い |
| 塗りつぶし | 見た目の色の連続領域 | 層ごとに結果が違う（はんこの内側が塗れない） | 焼き付け後に塗る。見た目通り | ラスタ化が必須で整合が難しい |
| undo | 単純（差分 1 種類） | 2 種類の履歴が必要 | コマンド履歴＋差分。焼き付けも 1 手として扱う | 単純だが容量大 |
| 後からの編集 | 不可 | オブジェクトのみ可 | 浮いている間のみ | 常に可 |
| 実装コスト | 低 | 中 | 中 | 高 |
| 幼児の期待との一致 | 高い | 低い（「消せない」「上に出る」） | 高い | 中 |

- 【事実】Toon Boom の資料では、ベクター層の消しゴムは形を切り取り、ビットマップ層の消しゴムは別系統で、プリセットも別。Pencil2D の利用者報告では、ベクターの消しゴムは頂点を消すので、描いた範囲外まで消える場合がある。つまり層ごとに消しゴムの意味が違うと混乱しやすい（案 B と D の弱点）。
- 【示唆・推奨】**案 C（幼児は浮かせる数 1 個、実質は案 A に近い）を推奨**。理由は (1) 重なりと消しゴム・塗りつぶしが「見たまま」で一貫し、幼児の期待に合う、(2) Tux Paint の Label と同じ「確定前だけ浮かせる」考え方で、再編集の需要は直前の 1 個にほぼ集中する（仮説）、(3) 履歴が単純。
- 【示唆】背景は別扱いにする。紙の色や塗り絵の線画は固定の背景層（消しゴムが現れさせる面）、ユーザーの描画はその上の透明ラスタ層とする。消しゴムはラスタ層の `destination-out` で透明にして背景を見せる（Tux Paint が背景を見せるのと同じ見え方）。塗り絵は線画を上に重ね（multiply など）、塗りは「背景＋ラスタを合成した見た目」で連続領域を判定し、結果は下のラスタ層に書く。これで線をはみ出さず、アンチエイリアスの縁の塗り残しも線画が隠せる。
- undo の方針【示唆】: 操作 1 回＝履歴 1 件。ペン・塗り・消しは「操作前の変更領域（矩形）の画像」、オブジェクトは操作前後の値を持つ。焼き付けも 1 件（直前のラスタ矩形＋オブジェクト一覧を記録）。undo 後に新しい操作をしたら redo は破棄。
- 幼児向けの画面は「もどす」ボタン 1 つ（内部は複数段）。redo は小学生向けのみ表示する案（Kid Pix も初期は 1 回のみの取り消し）。

## 5. 保存形式と容量

### 5.1 形式案【示唆】
IndexedDB に 2 つのストアを分ける: `drawings`（一覧用メタ情報と小さなサムネイル）と `drawingBlobs`（ラスタ PNG・閲覧用 PNG の Blob）。一覧は軽いストアだけを読む。

```json
{
  "schema": 1, "id": "…", "createdAt": "…", "updatedAt": "…", "appVersion": "…",
  "size": { "w": 1920, "h": 1080 },
  "background": { "kind": "paper", "color": "#ffffff" },
  "template": { "id": "nurie-001" },
  "raster": "blobKey",
  "preview": "blobKey",
  "thumb": "blobKey",
  "floating": [
    { "type": "stamp", "stampId": "dog-01", "stampVer": 1, "x": 640, "y": 360, "scale": 1.0, "rot": 0, "flipX": false },
    { "type": "shape", "kind": "circle", "x": 900, "y": 500, "w": 200, "h": 200, "rot": 0, "stroke": "#e53935", "fill": null, "lw": 8 }
  ]
}
```

- 再編集データ: ラスタ層 PNG（透明あり）＋浮いているオブジェクトの JSON。案 C では焼き付け済みのものは再編集できない。再編集を保存後も保持したいなら、保存時に焼き付けるか、「焼き付けない」かを選ぶ。既定は閉じる前に焼き付け、開き直した後に動かせるのは未確定の分だけにする案を提案。
- 閲覧用 PNG: 背景＋ラスタ＋オブジェクトを合成した 1 枚（共有・印刷・一覧表示用）。スタンプ画像そのものは保存せず ID とバージョンで参照（素材が差し替わった時の互換は `stampVer` で扱う）。
- 保護者向け書き出し: 既存のデータ書き出しに含める場合、画像を base64 で JSON に入れると約 1.33 倍に膨らむため、作品は別形式（zip や個別 PNG）にする案。【未確認】現行の書き出し実装は未調査。
- 自動保存: 一定時間の無操作や画面離脱時に下書きを保存し、閉じ忘れても消えないようにする案（Tux Paint はファイル名を聞かず保存、上書き／新規を選ばせる）。

### 5.2 容量の見積もり
- **計測（本調査）**: 合成の折れ線（8 色、各 40 点のランダムな線）を白地の 1920×1080 に描き `toBlob('image/png')`。環境は Playwright の Chromium 156（ヘッドレス・Windows）。実際の子供の絵ではなく、PNG の目安としてだけ使う。
  - 線 15 本: 273 KB / 80 本: 873 KB / 400 本: 1.50 MB。真っ白: 44 KB。
  - 3840×2160（DPR2 相当・80 本・線幅 2 倍）: 1.94 MB。960×540（80 本）: 392 KB。
  - 同じ画像を WebP にすると約 1/3〜1/4（1080p・80 本で 249 KB）。ただし WebP の符号化は 190〜555 ms と PNG より遅かった。
  - `toBlob`（PNG）は 1080p で 59〜122 ms。同期的に待たず、保存は操作の合間に行う。
  - Firefox は同じスクリプトを起動できず（`spawn UNKNOWN`、環境側）、計測していない【未確認】。
- **見積もり**【示唆】: 1 作品＝ラスタ PNG＋閲覧用 PNG＋サムネ（320×180 で 20〜60 KB 程度）。実際の絵は平らな塗りが多く、合成より小さくなる可能性が高いが未計測。上限を 1 枚 1.5 MB と仮定すると 1 作品約 3 MB、100 作品で約 300 MB。
- 保存先の上限（MDN）: Chromium は全ディスクの 60%、Firefox のベストエフォートは全ディスクの 10%または 10 GiB の小さい方。永続化は `navigator.storage.persist()`（Firefox は確認ダイアログが出る）。上限超過は `QuotaExceededError`。Firefox のプライベートウィンドウでは IndexedDB はメモリのみ。
- 【示唆】作品数の上限（例: 100 件）か古い順の整理案内を用意し、`navigator.storage.estimate()` で残量を見て保護者画面に表示する。書き込み失敗時は絵を失わないよう、画面上に保持したまま通知する。
- **undo 履歴のメモリ**: 1920×1080 の RGBA は 8,294,400 B（約 7.9 MiB）、3840×2160 は約 31.6 MiB。全画面スナップショットを 30 回保持すると 1080p で約 237 MiB、4K で約 950 MiB になり不適。→ 変更領域だけの差分を保存し、件数でなく合計バイト数で上限（例: 64〜128 MiB、最低 10 件は保持）を決め、古い順に捨てる。履歴を PNG 化して退避する案もあるが、1080p で 60〜120 ms かかるため、毎操作ではなく待機中のみ。【未確認】実機（Zorin・Linux）での処理時間。

## 6. ブラウザの制約と対策（Chromium / Firefox / Linux タッチ）

| 項目 | 事実 | 対策【示唆】 |
|---|---|---|
| `pointerType` / `pressure` | Chrome 55、Firefox 59（Android は 79）。`pressure` は圧力非対応機器でマウスは押下中 0.5。タッチで圧力が無い機器の値は MDN に明記なし | 筆圧は使わず線の太さは道具で固定。筆圧対応は将来の追加扱い |
| `getCoalescedEvents` | Chrome 58、Firefox 59、Safari 18.2。**セキュアコンテキストのみ**。Firefox Android では常に空配列を返す部分実装 | 現行アプリは 127.0.0.1 で配信（README）。【一般知識】localhost / 127.0.0.1 はセキュア扱い。空なら元のイベントを使うフォールバック。`typeof` で存在確認（既存の TraceCanvas も同様に存在確認している） |
| `getPredictedEvents` | Chrome 77、Firefox 89、Safari 18.2。予測は次のイベントまで有効 | 予測点は仮描きに限り、確定線には使わない。必須ではない |
| `touch-action` | `none` でパン・ズーム等を止められるが、**ジェスチャ開始後の変更は無効**。ブラウザが操作を奪うと `pointercancel` が飛ぶ。ページ全体に付けると拡大不可などアクセシビリティの問題 | 描画キャンバスにだけ `touch-action: none`（既存の trace と同様）。`contextmenu` を抑止（長押しメニュー対策） |
| パームリジェクション | 仕様上、ペンとタッチ併用機器では UA がペン使用中のタッチを無視でき、不意の接触で `pointercancel` を出すことがある。**制作者側はこれを止められない**。ページから有効化や制御する API は見つからなかった。`width`/`height` は接触面積を示すが、信頼性は機器依存【未確認】 | ブラウザ単体では「防げない」。アプリ側の緩和: (1) 描画中は `isPrimary` 以外の接触を無視 (2) `pointercancel` では描いた分を捨てずに確定（Sesame の「途中までを有効に」） (3) 手首が乗る下端にボタンを置かない (4) ペン検出後はタッチを無視する任意設定 (5) 接触面積の閾値は既定では使わない |
| 複数指 | 各接触に `pointerId`。タッチの最初の接触が `isPrimary` | 幼児モードは 1 本指固定。ピンチ等はくわしいモードのみ |
| ポインタキャプチャ | `setPointerCapture` で枠外に出ても追跡。タッチは暗黙のキャプチャあり | 描画開始時にキャプチャし、`pointerup`/`pointercancel` で終了 |
| 高 DPI | `devicePixelRatio` を掛けてバッキングストアを大きくし CSS で縮小するのが定石（MDN） | 作品の論理サイズは 1920×1080 などに固定し、画面は CSS で縮小表示。保存物が端末の DPR で変わらないようにする。描き味を優先して 2 倍で描く場合はメモリが 4 倍になる |
| キャンバス上限 | MDN は上限を記載せず。端末ごとに異なる（古い資料では iOS Safari が 4096×4096／約 1,677 万画素、Firefox は幅高さ 32,767 まで）。Chromium の現行上限は【未確認】 | 1920×1080（約 207 万画素）、DPR2 でも約 829 万画素に収まる。起動時に必要サイズの確保を試し、失敗したら縮小するフォールバック |
| 塗りつぶし | `getImageData` で読んで `Uint32Array` で処理する走査線方式（スパン塗り）が再帰より速い（Wikipedia: 2〜8 倍）。許容値・縁の扱いは別途必要 | **計測**: 1080p でほぼ白紙 20〜47 ms、線あり 5〜78 ms（初回 JIT 含む）、4K 27〜83 ms（Chromium ヘッドレス）。許容値 24 付きも同程度。実機は GPU からの読み戻しで遅くなる可能性【未確認】。読み取り用キャンバスは `willReadFrequently: true` が有効だが描画が遅くなる側面もある（MDN） |
| 塗り残し | アンチエイリアスの縁が許容値 0 だと塗り残る【一般知識・示唆】 | 許容値を少し持たせる、塗った領域を 1〜2 px 拡張、線画を最前面に重ねる |
| OffscreenCanvas | Chrome 69、Firefox 105、Safari 16.4。ワーカーで描画・`convertToBlob` 可 | 必須でなく、重い処理（塗り、書き出し）を主スレッドから外す選択肢。当面は主スレッドで足りる見込み（上の計測） |
| PNG 書き出し | `toBlob` は既定 PNG、非同期、解像度メタデータは 96dpi。汚染されたキャンバス（他オリジン画像）だと `SecurityError` | はんこ素材は同一オリジンで配信し汚染を避ける |
| IndexedDB | 構造化複製で Blob を保存できる【一般知識。MDN の Using IndexedDB には記載なし】。トランザクションは要求が無いと閉じる。未処理エラーは全体をロールバック | 大きな Blob は書き込みのトランザクションを 1 つにまとめ、`await` の間に他の処理を挟まない。失敗時は絵を残す |
| Firefox の Linux タッチ | 古い報告では X11 で `MOZ_USE_XINPUT2=1` が必要、効かない例もある。README にも記載あり（実機未確認） | 描画機能の受け入れ試験に Zorin + Firefox を含め、マウス扱いになる場合でも描ける作りにする（Pointer Events の `pointerType` に依存しない） |

その他【示唆】:
- 描画は `pointermove` ごとに確定先のキャンバスへ線分を追加し、画面更新は `requestAnimationFrame` でまとめる。座標は整数に丸めると速い（MDN の最適化指南）。
- 表示用キャンバスと「浮いている物」用のキャンバスを重ね、浮いている物の移動時に全体を再描画しない（MDN: 層を分けたキャンバス）。
- 浮いたオブジェクトの当たり判定は、見た目より一回り大きくする（幼児の指の太さ向け）。
- 回転・拡大はキャンバス変換で描く。スタンプ画像は表示サイズ以下のビットマップを用意して拡大描画を避ける（MDN）。
