# 二重起動の禁止と「起動中の窓を前面に全画面」の設計（single-instance-design.md）

- 状態: 実装済み。設計の本文（1〜7 章）のあとに、実装とレビューの記録（8 章）を付けた。設計と実装で違うところは 8.3 に集めた。公開の前の3回目の点検（2026-11-07）の指摘と対応は 8.6。
- 依頼: 「ブラウザアプリであるが、アプリの二重起動を禁止したい。もし二重起動しようとしたら、すでに起動中のものを前面に全画面表示してほしい」
- 調べたこと: OS まわりを付録 A、ブラウザまわりを付録 B に要点だけ載せた。
- 守ること: sudo・管理者権限を使わない／apt などで道具を足さない（Zorin に最初からあるものと Python 標準ライブラリ。ctypes で OS の共有ライブラリを呼ぶのは可）／端末のシステム設定を変えない／学習の記録（IndexedDB、オリジン `http://127.0.0.1:8765`）を消さない・オリジンを変えない・プロファイルを変えない（`--user-data-dir` を付けない）／外への通信をしない／人が見て判断する作業を作らない
- 印: 【要実機】= Zorin の実機でしか確かめられないこと（6 章に集めた）

## 0. 要点

### 0.1 決めたこと（短く）

1. **3つの層で守る。** (a) 起動スクリプトが起動中の窓を探して前に出す、(b) serve.py は変えない、(c) アプリの中で「画面は常に1つ」を Web Locks で守る。
2. **道 A（起動中の窓をそのまま前に出す）**: `manabi.sh` が補助 `deploy/zorin/mnwwindow.py`（Python 標準ライブラリ＋ctypes＋`libX11.so.6`）を呼び、X11 で見える「まなびのにわ」の窓を探す。見つかれば `_NET_ACTIVE_WINDOW` と `_NET_WM_STATE`（FULLSCREEN）を送り、前に出たことを確かめて終わる。**新しい窓は開かない**。遊んでいた途中の画面がそのまま全画面で出る。
3. **Wayland セッションでも道 A が効く場面を増やす**: `manabi.sh` が Chromium 系を起動するときに `--ozone-platform=x11` を付ける（ブラウザのプロセスが新しく立ち上がるときだけ効き、XWayland の窓になる）。分数スケーリングが有効な端末では付けない（ぼやけるため）。Firefox には付けない（2.1.5）。
4. **道 B（前に出せないときの代わり）**: 窓が見つからない（Wayland ネイティブで動いている、Firefox でアプリのタブが裏にある など）・前に出せないときは、今までどおり新しい窓（タブ）を開く。アプリの中で **新しい画面が残り、前の画面は保存を済ませて自分を閉じる**（「引き継ぎ」）。新しい画面は起動画面から始まり、**「はじめる」のタップで全画面**になる。前の画面が自分を閉じられないとき（画面を移したあとで、履歴が2件以上）は、その窓を `./?retired=1` に置き換えて「べつの まどで ひらいています」とだけ出し、記録を書かない。
5. **画面の移動でブラウザの履歴を増やさない案は採らない**（2.3.4）。ブラウザの「戻る」と、おえかきの「もどると前の作品が開く」を残す。
6. **起動を1本ずつにする**: `manabi.sh` を `flock` で直列にする（アイコンの連打）。ブラウザを開いたあと、窓が見つからなかったときだけ、窓が出るまで（最大 5 秒、X11 で見える場合）鍵を持ち続ける。
7. **最初の起動は全画面にしない**（依頼どおり。2.4.1）。
8. `.desktop`・systemd の単位ファイル・serve.py は変えない。→ 更新の仕組み（保護者画面の「更新する」）だけで、入れている端末に届く。

### 0.2 決めたこと（D1〜D6）と、この設計での扱い

| # | 判断 | 決め方 | 理由（詳しくは） |
|---|---|---|---|
| D1 | 要件 OP-07「全画面を強制しない」を変える | **変える**。「最初の起動は全画面にしない。2回目の起動のときだけ、起動中の窓を全画面で前に出す」。やめ方（F11 キー・Esc キー）を README と保護者画面に書く | 依頼そのもの（2.4） |
| D2 | OS から前に出せないとき、新しい画面を残す | **採る。ただし代わりの道（道 B）としてだけ**。前に出せる環境（X11・XWayland の窓）では、依頼どおり起動中の窓を前に出して全画面にし、新しい窓は開かない（道 A） | ページは自分の窓を前に出せない。古い方を残すと、Chromium では何も前に出ない（2.3.2） |
| D3 | 画面の移動で履歴を増やさない（`replaceState` だけにする） | **採らない**。`router.ts`・おえかきの `pushState` は変えない。要件 OP-08 は作らない | 「戻る」とおえかきの「もどると前の作品」を失う損が大きい（2.3.4） |

| D5 | 最初の起動 | 全画面にしない | 依頼に無い。保護者が準備で使う画面を隠さない（2.4.1） |
| D6 | 読み込み中にもう一度押した（連打） | `flock` で1本ずつにし、2本目以降は起動中の窓の前面化と全画面だけをする | 「起動中に押したら前に全画面」を同じ規則で通す（2.1.7） |

あわせて、Zorin 17.3 以降の新規インストールの既定のブラウザは Brave（Firefox ではない）。README の記述を直した（付録 A）。

## 1. 全体の考え方

### 1.1 なぜ3つの層か

- **ページ（ブラウザの中）からは、自分の窓を前に出せない。** Chromium は 2012 年から自分への `window.focus()` を許さない。Firefox は `dom.disable_window_flip=true`。Service Worker の `WindowClient.focus()` も通知のクリックのときだけ（付録 B）。
- **ページからは、ユーザー操作なしに全画面にできない**（`requestFullscreen` は、その窓でのタップ・キー入力が要る。別の窓の操作は引き継がれない。例外の設定は管理者のポリシーだけ。付録 B）。
- **OS の側からなら、X11 の窓は前に出して全画面にできる**（EWMH。Mutter 43.8・46.2 のソースで確認。XWayland の窓にも効く。付録 A）。**Wayland ネイティブの窓は外から前に出せない**（同 3 章）。
- **起動スクリプトの寿命はアプリの寿命ではない**（`manabi.sh` はブラウザを起動してすぐ終わる。いまのコードの調べ）。窓は OS で探すか、ページ同士で見つけるしかない。

→ 前に出す・全画面にするのは OS の側（a）。前に出せない場合でも「画面は1つ」を守るのはページの側（c）。この2つで足りるので、配信（b）は変えない。

### 1.2 流れ

```
アイコン（.desktop は今のまま）
  └─ manabi.sh
       0. flock で1本ずつ（ほかの起動が終わるまで最大 20 秒待つ。待ちきれなければ何もせず終わる）
       1. 配信を確かめる・起動する
       2. 使うブラウザの種類を決める（何も起動しない）
          mnwwindow.py focus --browser <種類> ─┐
            X11 で「まなびのにわ」の窓を探す      │ 見つかって前に出た（終了コード 0）
            （Chromium 系なら Firefox の窓は探さない）
            → 前面化＋全画面 → 確かめる         └─▶ 終わり【道 A：前の画面がそのまま全画面で前に】
          見つからない（3）・前に出せない（4）・X11 が無い（5）・ほか
       3. ブラウザで開く（Wayland で Chromium 系なら --ozone-platform=x11 を足す）
       4. 2 の結果が「窓が無い」（3）だったときだけ、mnwwindow.py wait --browser <種類>（窓が出るまで最大 5 秒。そのあいだ鍵を持つ）→ 終わり

ブラウザの中（main.tsx の最初。Service Worker の登録・IndexedDB・描画より前）
  Web Locks「manabi-no-niwa:main」を取る
   ├─ 取れた → ふつうに始める（これが最初の起動）
   └─ ほかの画面が持っている → BroadcastChannel で「いる？」と聞く（読み込み直しは 0.4 秒、それ以外は 1 秒待つ）
        ├─ 返事あり
        │    ├─ 「戻る」「進む」での読み込み → 鍵を奪わず、この窓が引き下がる（べつの まどで ひらいています）
        │    └─ それ以外 → 鍵を奪う（steal）→ 前の画面が保存して閉じるのを待つ（最大 5 秒）→ 始める。「はじめる」のタップで全画面【道 B：引き継ぎ】
        └─ 返事なし（読み込み直しの直後・凍結した画面）→ 鍵を奪ってすぐ始める（全画面にはしない）
  鍵を奪われた画面 → 題名を変える → 音を止める → 画面を片付ける（React の unmount。保存の後片付けが走る）
                    → 終わっていない保存が全部終わるのを待つ（最大 4 秒）→ 0.3 秒待つ →「終わった」を知らせる
                    → window.close() → 閉じられなければ ./?retired=1 に置き換えて「べつの まどで ひらいています」だけを出す
  引き下がった画面 → 2 秒おきに鍵を見て、空きが続けて2回出たら、自分で始め直す
```

## 2. 層ごとの仕組み

### 2.1 (a) 起動スクリプト（`manabi.sh` ＋ `mnwwindow.py`）

#### 2.1.1 `manabi.sh` の動き（実装は `deploy/zorin/manabi.sh`）

0. **起動を1本ずつにする**: 鍵のフォルダは `$XDG_RUNTIME_DIR`、無ければ `$STATE_DIR`（`~/.local/state/manabi-no-niwa`）。**自分のフォルダ（`[ -O ]`）で書けるときだけ**使う。鍵のファイルがリンクや、ほかの利用者のファイルなら使わない（鍵なしで進む）。`exec 9>>鍵` のあと `flock -w 20 9`。取れなければ（終了コード 1）何もせず終わる。時間切れ以外の失敗は鍵なしで進む。`flock` が無い環境でも進む。
1. **配信の確かめ**: `python3 -I -`（今いるフォルダの `json.py` などを読み込まない。アイコンから開くと今いるフォルダは HOME のため）。全体の期限は 6 秒（SIGALRM。urllib の timeout は1回ごとの期限で、1 秒に 1 バイトずつ返すものには効かないため）。戻り値は 0 = まなびのにわの配信／1 = 何も待ち受けていない／それ以外 = 別のものが答えている（エラー）。
2. **前面化**: 先に、使うブラウザを決める（3 と同じ決め方を 1 か所に持ち、2 と 3 で同じ結果を使う。`command -v` で探すだけで、何も起動しない）。種類は `chromium`（Chromium 系）・`firefox`・`other`（xdg-open・見つからない・`MANABI_BROWSER` で種類が分からない）の 3 つ。`MANABI_BROWSER` の種類は、先頭の語の basename だけで見る（中身は実行も展開もしない）。`win focus --browser <種類>` の終了コードを `focus_rc` に覚える。0 なら、新しい窓を開かずに終わる。ブラウザが見つからない・`MANABI_BROWSER` のコマンドが無いという誤りは、今までどおり 3 で出す（窓がすでにあれば、2 で前に出して終わる）。
3. **ブラウザで開く**: 2 の前に決めたブラウザを使う。`MANABI_BROWSER` を優先。次に chromium / chromium-browser / google-chrome / google-chrome-stable / brave-browser を `--app`、無ければ firefox（通常のタブ）、無ければ xdg-open。Chromium 系は、`win ozone-flag` の答えが `--ozone-platform=x11` ちょうどのときだけ、`--app` の前に足す。`MANABI_BROWSER` に `--ozone-platform=…` か `--ozone-platform-hint=…` が書いてあれば、足さない（後ろの指定が勝つため、足すと保護者の指定が黙って無視される）。Firefox・xdg-open には付けない。
4. **待ち**: `focus_rc` が 3（窓が無い）のときだけ、`win wait --timeout 5 --browser <種類>`。窓はあるが前に出せなかった（4）・X11 が使えない（5）・補助の不具合（1・2・そのほか）のときは待たない（古い窓を見つけて 0 秒で終わる、または失敗して待つだけになるため）。

- `launch()` と `win()` と配信の起動には `9>&-` を付け、鍵の fd（9）を子に渡さない（渡すと、ブラウザが生きているあいだ鍵が外れず、次の起動が 20 秒待って何もせずに終わる）。エラーのダイアログを出す前にも鍵を外す。
- `MANABI_SINGLE_INSTANCE=0` は、前面化・`--ozone-platform`・待ちを止める（困ったときの逃げ道。開発者向け。アプリの中の「画面は1つ」は止まらない）。`MANABI_OZONE=x11|native` は `--ozone-platform=x11` を付けるかを決める（2.1.5）。環境変数の値は、実行も展開もせず、そのままの文字として扱う。
- `mnwwindow.py` が無い配置（古い版の `install.sh` で入れた場合など）では今までどおりに動く。
- `-I`（隔離モード）: 環境変数 `PYTHON*`・利用者の site・今いるフォルダを読まない。`mnwwindow.py` は1ファイルで、ほかを import しないので使える。`-B`: `__pycache__` を作らない（更新の仕組みの約束と同じ）。

#### 2.1.2 `mnwwindow.py` の約束

- 1ファイル。Python 3.10 で動く書き方（`match` 文・`datetime.UTC` を使わない）。標準ライブラリと ctypes だけ。500 行ちょうどで、NF-06 の目安（400 行）を超えている（X11 の下まわり・判定・やり直し・記録を1ファイルにしたため）。行数の試験の上限（500 行）と同じで、余裕が無い（8.5）。
- 使い方: `python3 -I -B mnwwindow.py [--log FILE] <コマンド> [引数]`

| コマンド | すること | 終了コード |
|---|---|---|
| `focus [--deadline 2.5] [--browser chromium\|firefox\|other]` | アプリの窓を探して前面化＋全画面。前に出たことを確かめる。`--browser` は `manabi.sh` が使うブラウザの種類（省略は `other`） | 0 = 前に出た（全画面は最善を尽くす。結果は記録に）／3 = 窓が無い／4 = 窓はあるが期限内に前に出なかった／5 = X11 が使えない（`DISPLAY` が空・`libX11.so.6` が読めない・`XOpenDisplay` が失敗）／2 = 使い方の誤り（`--browser` の値が違うときも）／1 = 予想外の失敗 |
| `wait [--timeout 5] [--browser chromium\|firefox\|other]` | アプリの窓が現れるまで 0.1 秒ごとに探す（何も送らない）。窓の探し方は `focus` と同じ | 0 = 現れた／3 = 時間切れ／5 = X11 が使えない |
| `ozone-flag <ブラウザのコマンド>` | `--ozone-platform=x11` を付けるべきなら、それだけを1行出す。付けないなら何も出さない | いつも 0 |

- `manabi.sh` は `focus` の 0 だけを「終わってよい」と見なす。**0 以外はすべて「今までどおり開く」**（安全な側に倒す）。
- どのコマンドも、最初に 10 秒の時間切れを仕掛ける（`arm_timeout`。X が固まっても 10 秒ほどで必ず終わる）。SIGALRM の handler を明示して（`os._exit(1)`。終了コード 1・出力なし。親が SIGALRM を無視にして起動していても効く）`alarm(10)` を仕掛け、あわせて別のスレッドの見張り（`faulthandler.dump_traceback_later(11, exit=True)`。やはり終了コード 1）を置く。libX11 の呼び出しの中（Xlib は EINTR で読み直す）で固まると、Python の handler は走れないため、見張りが補う（3回目の点検 launcher-6。8.6）。Xlib のエラーハンドラーは何もしないものに差し替える（走査中に窓が閉じても落ちない）。ctypes の注意点（`restype`・`argtypes`、format 32 は C の `long`、`XFree`、CFUNCTYPE の参照を保持）は 付録 Aのとおり。
- X の部分は小さな「下まわり」（`X11Backend`。ctypes）にまとめ、判定とやり直しの規則は下まわりを受け取る関数にする（試験では偽物に差し替える。5 章）。下まわりが持つ操作: 窓の一覧（重なり順）、`WM_CLASS`、題名（`_NET_WM_NAME`）、いま前の窓（root の `_NET_ACTIVE_WINDOW`）、全画面か（`_NET_WM_STATE`）、サーバー時刻、前面化を送る、全画面を送る、`XSync`。

#### 2.1.3 窓の見つけ方

対象は root の `_NET_CLIENT_LIST_STACKING`（無ければ `_NET_CLIENT_LIST`）に並ぶ窓。Wayland セッションでは XWayland の窓だけが並ぶ。

```
APP_TITLE = "まなびのにわ"
SUFFIX   = r"\s[—–-]\s(Mozilla Firefox|Firefox|Brave|Chromium|Google Chrome)$"
base(t)  = 題名 t の末尾から SUFFIX を1回だけ取り除いたもの
強い一致 = WM_CLASS の res_name が "127.0.0.1" かつ base(題名) == APP_TITLE
弱い一致 = WM_CLASS の res_class を小文字にしたものが
            {firefox, firefox-esr} のどれか かつ base(題名) == APP_TITLE        （Firefox のタブの窓）
          または {brave-browser, chromium, chromium-browser, google-chrome} のどれか かつ 題名 == APP_TITLE
                                                                          （末尾を取り除かない。末尾の付かないアプリ窓だけ）
選び方   = 強い一致のうち重なり順でいちばん上 → 無ければ弱い一致のうちいちばん上
--browser chromium のとき: 弱い一致の候補から {firefox, firefox-esr} を外す（強い一致は種類に依らない）
```

- **res_name `127.0.0.1`**: Chromium 系の `--app=http://127.0.0.1:8765/` の窓は、URL から res_name が `127.0.0.1` になる（ポート・ハッシュは入らない。付録 A）。これは**すでに動いているブラウザに引き渡された起動でも付く**ので、いちばん確かな印になる。
- **題名はちょうど「まなびのにわ」**（`index.html` の `<title>`。`src` に `document.title` を変える所は、引き下がるときの変更だけ）。ふつうのタブの窓では末尾にブラウザ名が付くので、それだけを取り除いてから比べる。「まなびのにわ - GitHub」のような別のページは一致しない。
- **Chromium 系の弱い一致は、末尾の付かない題名（アプリ窓）だけ**。`manabi.sh` は Chromium 系を必ず `--app` で開くので、ふつうは強い一致になる。弱い一致は、res_name の付き方が実機で違っていたときの保険として残した。ふつうのタブ（「まなびのにわ - Brave」）は選ばない（点検で、別のサイトの窓を前に出す害が指摘されたため。8.4）。
- **引き下がった画面の題名は「とじた がめん（まなびのにわ）」**にする（2.3.3）。「まなびのにわ」で始まらないので、閉じきれなかった古い窓を前に出してしまうことは無い。
- Firefox は、その窓でアプリのタブが前にあるときだけ題名で分かる。裏のタブは外から選べない（付録 A）→ 見つからない扱いにして道 B。
- **Chromium 系で開く端末では、Firefox の窓を候補にしない**（3回目の点検 launcher-1。8.6）。Firefox の弱い一致は、出どころ（どのサイトのページか）を外から確かめる手が無く、題名がちょうど「まなびのにわ」の別のサイトのタブも一致してしまう。そこで `manabi.sh` が使うブラウザを先に決めて `--browser` で渡し、`chromium` のときは Firefox の class を弱い一致から外す。外した結果、窓が見つからなければ、新しい窓を開く側（道 B）に進むだけなので、安全な側に倒れる。`firefox`・`other`・省略は今までどおり（Chromium 系の弱い一致も候補に残る。8.5）。
- 記録（launch.log）には、見つけた窓の番号・res_class・全画面になったかだけを書く。**ほかのアプリの窓の題名は書かない**（個人の情報が入りうる）。


使わない手とその理由:

| 手 | 使わない理由 |
|---|---|
| `--class=...`（res_class を変える） | 本体のプロセスが新しく立ち上がるときだけ効く。しかもそのプロセスのふつうの窓まで同じ class になり、ドックのまとまりが崩れる（付録 A） |
| `.desktop` に `StartupWMClass=127.0.0.1` | GNOME Shell が窓をこのアプリと結びつけ、アプリ一覧・ドックから開くと **スクリプトを通らずに Shell が窓を前に出すだけ**になる（全画面にならない）。`.desktop` の変更は入れ直しが要る（更新の仕組みは `.desktop` を書き換えない。updater-design.md 7.3・14 章） |
| `_NET_WM_PID` とプロファイルの `SingletonLock` | Flatpak・snap では PID の空間が違う。res_name と題名で足りる |
| 起動の URL を `/index.html` にして res_name を変える | 古い窓（`/` で開いたもの）と混ざる。得るものが小さい |

#### 2.1.4 前面化と全画面の送り方・確かめ方

- 送るもの（どちらも root へ、`SubstructureRedirect|SubstructureNotify`。付録 A）:
  - `_NET_ACTIVE_WINDOW`: `data.l = [2（ページャー＝利用者の操作の代わり）, 時刻, 0, 0, 0]`
  - `_NET_WM_STATE`: `data.l = [1（ADD）, _NET_WM_STATE_FULLSCREEN, 0, 2, 0]`
  - 送ったら `XSync`。
- 時刻と、やり直しの予定（期限 2.5 秒）:

| 開始からの時刻 | 送る時刻 | ねらい |
|---|---|---|
| 0 秒 | **いまのサーバー時刻**（自分の小さな窓のプロパティに 0 バイト追記 → PropertyNotify の時刻。ICCCM） | フォーカスを奪う防ぎを通る。最小化を戻し、別のワークスペースなら切り替える |
| 0.5 秒 | 0 | XWayland と Mutter の時計がずれて「古い時刻」と見なされた場合の保険（同じワークスペースなら前に出る。ジャーナルに "Buggy client" の警告が1行出るが害は無い） |
| 1.2 秒 | サーバー時刻 | オーバービュー・Zorin メニューが閉じきる前（Shell がつかみ中は黙って捨てられる）の保険 |
| 1.9 秒 | 0 | 同上 |

- 確かめ: 0.1 秒ごとに root の `_NET_ACTIVE_WINDOW` が目当ての窓になったかを見る。なったら `_NET_WM_STATE` に FULLSCREEN があるかを見て、無ければ全画面だけを1回送り直し、最大 0.5 秒待つ。全画面にならなくても「前に出た」なら 0 で終わる（記録に `fullscreen:false`）。
- 途中で窓が消えたら選び直す。選べなければ 3。期限までに前に出なければ 4。
- Chromium は窓の管理が付けた全画面を自分の全画面（F11 と同じ）として扱う（付録 A）。Firefox も窓の全画面で自分の全画面に入る。【要実機】見た目（タイトルバー・タブが消えるか）。

#### 2.1.5 X11 と Wayland の分け方（`ozone-flag` の規則）

前面化（`focus`）はセッションを問わず「X11 で見える窓か」だけで決まる（Xorg ならすべての窓、Wayland なら XWayland の窓）。セッションで分けるのは、ブラウザをどう起動するかだけ。

`ozone-flag <ブラウザ>` は上から順に見て、最初に当たった行で決める:

| # | 条件 | 出すもの |
|---|---|---|
| 1 | `MANABI_OZONE=x11` | `--ozone-platform=x11` |
| 2 | `MANABI_OZONE=native` | なし |
| 3 | `XDG_SESSION_TYPE` が `wayland` でない | なし（Xorg ではもともと X11） |
| 4 | ブラウザが Chromium 系でない（`manabi.sh` の `is_chromium_family` と同じ規則: 名前に chrom・brave・edge・vivaldi・opera） | なし |
| 5 | `DISPLAY` が空（XWayland が無い） | なし（付けると起動できない） |
| 6 | `gsettings get org.gnome.mutter experimental-features`（2 秒で打ち切り。読むだけ）に `scale-monitor-framebuffer` があり、`xwayland-native-scaling` が無い | なし（分数スケーリングで XWayland の窓がぼやけるため） |
| 7 | それ以外 | `--ozone-platform=x11` |

- `--ozone-platform=x11` は、その起動でブラウザのプロセスが**新しく立ち上がるときだけ**効き、すでに動いているプロセスに引き渡される起動では無視される（付録 A）。だから「動いているか」を調べずに毎回付けてよい。【要実機】引き渡しのときに害が無いこと（Brave）。
- 副作用（README に書く）: そのブラウザのプロセスが動いているあいだ、保護者が後から開くふつうの Brave の窓も XWayland になる。プロファイル・オリジン・IndexedDB は変わらない。ブラウザを全部閉じれば元に戻る。
- **Firefox には `MOZ_ENABLE_WAYLAND=0` を付けない**。(1) すでに Wayland で動いている Firefox に X11 の起動から渡すと、「Firefox は起動していますが応答しません」が出るおそれがある（引き渡しの仕組みが X11 と D-Bus で違う。【要実機】）。(2) X11 の Firefox はタッチの扱いが変わるおそれがある（README に `MOZ_USE_XINPUT2` の注意がある）。Firefox の Wayland セッションは道 B に任せる。
- `focus` は Wayland セッションでも `DISPLAY` に接続する。XWayland がまだ動いていなければ、そこで立ち上がる（GNOME の「必要なときに起動」）。最初の1回だけ 1 秒ほど遅れることがある【要実機】。

#### 2.1.6 前に出せなかったときの代わり

| `focus` の結果 | よくある場面 | manabi.sh がすること | 起きること |
|---|---|---|---|
| 0 | 道 A が効いた | 終わる | 前の画面がそのまま全画面で前に |
| 3 | アプリがまだ開いていない（ふつうの1回目）／Wayland ネイティブで見えない／Firefox でアプリのタブが裏 | 今までどおり開く | 1回目ならふつうに開く。開いていたなら道 B（引き継ぎ） |
| 4 | 画面のロック中・別のワークスペースで時刻が使えなかった・Shell のつかみが続いた | 今までどおり開く | 道 B（新しい窓が前に残る） |
| 5 | X11 が無い（XWayland が無効など） | 今までどおり開く | 道 B |
| 1・2・そのほか | 補助の不具合 | 今までどおり開く | 道 B（少なくとも今より悪くならない） |

- 4 のときに「何もしない」案もあるが、子供から見ると「押したのに何も出ない」になる。道 B なら少なくともアプリが前に出る（前の画面の続きは失うが、記録は残る）。こちらを採る。

#### 2.1.7 起動の直列化（`flock`）と `wait`

- `flock` は util-linux（Zorin に必ずある）。鍵のファイルは `$XDG_RUNTIME_DIR/manabi-no-niwa-launch.lock`（ログアウトで消える一時の場所）。無ければ `$STATE_DIR`（uninstall.sh が消す）。`flock` が無い環境（Git Bash など）では直列化をせずに進む。
- **鍵の fd（9）を子に渡さない**（serve.py・ブラウザ・補助の起動にすべて `9>&-`）。渡すと、ブラウザが生きているあいだ鍵が外れず、次の起動が 20 秒待って何もせずに終わる。
- ブラウザを開いたあと、**窓が見つからなかった（`focus` が 3）ときだけ** `wait --timeout 5` で、窓が X11 に現れるまで鍵を持つ。そのあいだに押された2回目は鍵を待ち、窓が現れたあとで `focus` → 道 A（前に出て全画面）。D6 の「連打でも同じ規則」。
  - Wayland ネイティブで窓が見えない場合は 5 秒待って終わる。そのあいだの2回目は 5 秒遅れてから道 B になる（まれ。害は無い）。
  - `focus` が 3 以外のときに `wait` を呼ばないのは、(1) 窓はあるが前に出せなかった（4）のときは、新しい窓の前に古い窓が見つかって 0 秒で終わり、新しい窓が出る前に鍵が外れて連打で窓が増える、(2) X11 が使えない（5）や打ち切りのときは `wait` も同じように失敗するか 10 秒の打ち切りまで待つ、ため。
- 鍵を持つ時間の上限: 配信の確かめ（6 秒）＋ `focus`（最大 10 秒）＋ `wait`（最大 5 秒）。待つ側は 20 秒で諦める。
- ほぼ同時の2回（自動起動と手動など）の配信の取り合いは、今の処理（配信の起動待ちの「起動した配信が終わった。ほぼ同時に別の起動が先に動いた場合は、それを使う」）がそのまま残る。

#### 2.1.8 記録（`launch.log`）

- 場所: `~/.local/state/manabi-no-niwa/launch.log`（`$STATE_DIR`。uninstall.sh が今も消している場所）。
- `mnwwindow.py` が1回ごとに1行の JSON を足す。例: `{"t":"2026-11-20T10:24:01","cmd":"focus","session":"wayland","result":0,"window":"0x3a00004","class":"Brave-browser","match":"strong","fullscreen":true,"attempts":1,"ms":140,"browser":"chromium"}`。`ozone-flag` は `{"cmd":"ozone-flag","browser":"brave-browser","flag":"--ozone-platform=x11","reason":7}`。`browser` は、`focus`・`wait` では `--browser` の種類（chromium・firefox・other）、`ozone-flag` では渡されたコマンドの名前（basename）。
- 書き方: 同じフォルダに一時のファイル（`tempfile.mkstemp`。0600）を作って `os.replace` で置き換える。読むときはリンクをたどらず（`O_NOFOLLOW`）、ふつうのファイルでなければ空とみなし、大きすぎれば末尾の 1 MiB だけを読む。→ 記録がほかのファイルへのリンクでも、リンク先を書き換えない。10 秒の打ち切りが書き込み中に来ても、半端な記録が残らない（一時のファイルが残ることはある）。フォルダは 0700 で作る。
- 書くたびに 200 行を超えた分を前から捨てる。書けなくても動きは止めない。ほかのアプリの窓の題名・URL は書かない。
- 鍵を持たずに動いたとき（`flock` が無い環境）は、同時の書き込みで行が消えることがある。実機での確かめ（device-checklist）にだけ使うので、そのままにした。
- 製品の動きで人に読ませることはしない。


### 2.2 (b) serve.py の役目 → **変えない**

#### 2.2.1 変えない理由

1. **起動スクリプトは「ページが開いているか」を知らなくてよい。** 窓が X11 で見つかれば前に出す。見つからなければ開く。開いていた場合の重なりはアプリの中で片付く（2.3）。開いているかを知っても、することは変わらない。
2. **知らせる仕組みは配信より Web Locks の方が確か。** 配信への定期の合図は、裏の窓でタイマーが間引かれる（Chromium は隠れて 5 分で 1 分おき）ので、閉じたのか間引かれたのか区別できない。閉じた知らせ（`sendBeacon`）は POST で、落ちたときには届かない。
3. **serve.py は更新の仕組み（updater-design.md）が大きく書き換える**（`do_POST`・窓口・合言葉・再起動）。ぶつかる所を作らない。
4. 守る口が増えない（攻撃の面が広がらない）。

#### 2.2.2 将来、要るようになったときの形（今は作らない）

「Firefox と Brave で同時に開いた」（2つのブラウザの画面はお互いに見えない）まで止めたくなったときだけ。

- `GET /__manabi/instance/events`（ページがつなぎ続ける。Server-Sent Events）: 配信がつないでいる数を数え、新しくつながった画面より古い画面に「引き下がって」を送る。15 秒ごとに空の行を送って切れたのを知る。同時に 8 本まで。
- `GET /__manabi/instance`（起動スクリプトが読む）: `{"open": <数>}`。
- 守り（updater-design.md 5.4 と同じ考え）: `Host` が `127.0.0.1:8765`・`localhost:8765` だけ（無い要求も断る）／`Sec-Fetch-Site` が無いか `same-origin`（`cross-site`・`same-site` は 403）／CORS の見出しを返さない／`Cache-Control: no-store`・`X-Content-Type-Options: nosniff`・`Cross-Origin-Resource-Policy: same-origin`／GET だけ（ほかのメソッドは 405）。Service Worker は `/__manabi/` を素通しにする（updater-design.md 6.6 節で入る）。
- 作るなら、更新の仕組みが入ったあとの serve.py に、窓口の振り分けを1つ足す形にする。

### 2.3 (c) アプリの中の保険

#### 2.3.1 役割の決め方（`src/core/instance/instance.ts`）

`main.tsx` の最初（`startOffline()`・描画より前）で `claimInstance()` を待つ。役割は次のどれか:

| 役割 | 意味 | main.tsx がすること |
|---|---|---|
| `primary`（`takeover:false`） | ふつうの起動 | 今までどおり始める |
| `primary`（`takeover:true`） | 生きている前の画面から引き継いだ | 今までどおり始める。「はじめる」で全画面（2.4.3） |
| `retired` | `?retired=1` で開かれた（閉じきれなかった前の画面）、または「戻る」「進む」の読み込みで、生きている画面がいた | 「べつの まどで ひらいています」の画面だけを出す（2.3.5） |
| `unsupported` | Web Locks が無い・使えない（例外）、試験の旗、ほかのページの枠（iframe）の中 | 今までどおり始める（守りなし） |
| `superseded` | 始める前に、さらに新しい画面に鍵を奪われた | 何も始めずに引き下がる |

手順（名前: 鍵 `manabi-no-niwa:main`、知らせ BroadcastChannel `manabi-no-niwa:instance`）:

1. `?retired` があれば `retired`（題名を「とじた がめん（まなびのにわ）」にする）。
2. 試験の旗（`sessionStorage['mnw:test:multiWindow'] === '1'`）、`navigator.locks` が無い、ほかのページの枠の中なら `unsupported`。
3. `navigator.locks.request(LOCK, {ifAvailable:true}, cb)` — 取れたら鍵を持ち続け（`cb` は終わらない Promise を返す）、`primary`/`takeover:false`。
4. 取れなければ、0.1 秒おきに3回まで 3 をやり直す（**読み込み直しの直後**は、前の文書の鍵が外れるのが少し遅れることがあるため）。
5. まだ取れなければ、`{t:'ping', from:<自分のID>}` を送り、`{t:'pong', to:<自分のID>, from:<答えた画面のID>}` を待つ。待つ時間は、読み込み直し（`navigation` の type が `reload`）なら 0.4 秒、それ以外は 1 秒。
   - 返事あり（生きている画面がいる）:
     - 開かれ方が `back_forward`（「戻る」「進む」）なら、鍵を奪わず、この窓が `retired` になる（題名を変え、知らせの口を閉じる）。使っている窓を追い出さないため。
     - それ以外は `request(LOCK, {steal:true}, cb)` → **答えた画面からの** `{t:'retired', from:<答えた画面のID>}` を最大 5 秒待つ → `primary`/`takeover:true`。関係ない画面の `retired` では始めない。
   - 返事なし（読み込み直しの前の文書・凍結した裏の画面・離れる最中の画面）→ `steal` → 待たずに `primary`/`takeover:false`。凍結していた画面は、戻ったときに奪われたことを知って引き下がる。
6. `request()` が例外（SecurityError など）なら `unsupported`。

鍵を持つ画面は:
- `ping` に `pong` を返す（引き下がり中・離れる最中（`pagehide` のあと）は返さない）。
- `request()` の Promise が AbortError で失敗したら（= 奪われた）、2.3.3 の引き下がりをする。**始める前（引き継ぎ待ちのあいだ）に奪われた場合も同じ**（3つ目の画面が来たとき。描画していなければ片付けは空振り）。
- `pageshow` で `event.persisted === true`（戻る・進むのキャッシュから戻った）なら `location.reload()`（キャッシュに入るあいだに鍵が外れていた場合に、鍵なしで動くのを防ぐ）。

ID は `crypto.randomUUID()`（`127.0.0.1` は安全なコンテキストなので使える）。

定数（`INSTANCE_TIMING`・`LOCK_WATCH_TIMING`）:

| 定数 | 値 | 理由 |
|---|---|---|
| 鍵のやり直し（ifAvailable） | 3 回・0.1 秒おき | 読み込み直しの直後の鍵の外れ待ち |
| 返事を待つ（ping） | 1 秒（読み込み直しは 0.4 秒） | 手元が少しふさがっているだけの画面を、凍結した画面と見まちがえない。読み込み直しでは前の文書は返事をしないので短く |
| 前の画面の終わりを待つ | 5 秒 | 前の画面の後片付けの上限（4 秒）＋余裕。この間に新しい窓の背景は紙の色で出ている（CSS が先に読まれる） |
| 後片付けの上限 | 4 秒 | 関数の実行と、終わっていない保存の待ちの合計 |
| 片付けのあとの待ち | 0.3 秒 | 送りっぱなしの書き込み（回の終わりの時刻など）が終わる時間 |
| 閉じられなかったと見なす | 0.3 秒 | `window.close()` の結果を待つ |
| 鍵の見張りの間隔 | 2 秒（間の最短 1.5 秒） | 引き下がった画面が、鍵が空いたかを見る |
| 見張りで「空き」が続けて出る回数 | 2 回 | 更新の読み込み直しで鍵が一瞬空くのに反応しない |

試験のときだけ（`localStorage['mnw:test']==='1'`）、`window.__mnwInstance = {role, takeover}` を出す。


#### 2.3.2 なぜ「新しい画面が残る」か（依頼の「2つ目が自分を閉じる」を逆にした理由）

- 2つ目の画面ができるのは、道 A が効かなかったときだけ（Wayland ネイティブ・Firefox の裏のタブ・前に出せなかった・手でアドレスを開いた など）。
- そのとき **古い画面を残して新しい画面を閉じると**: Chromium の `--app` 窓では、新しい窓が一瞬出て消えるだけで、古い窓は前に出ない（ページからは前に出せない。付録 B）。子供から見ると「押したのに何も起きない」。
- **新しい画面を残すと**: 新しい窓（タブ）はブラウザと OS が前に出す。アプリが前に出て、窓は1つになる。全画面は「はじめる」のタップで入れる（タップはどのみち要る。音を出すため VO-05）。
- 失うのは前の画面の「いまの場面」だけ。記録は1問ごと・回の終わりに書いていて、つづき（drafts）も残るので、学習の記録は失わない。
- 「1つ目に知らせて前面化を試みる」は、ページからはできない（付録 B）ので作らない。前面化は道 A（OS の側）だけで行う。

#### 2.3.3 前の画面の引き下がり（奪われた画面の順番）

1. 題名を「とじた がめん（まなびのにわ）」にする（起動スクリプトが前に出さないように）。`pong` を返すのをやめる。
2. 引き継ぎ待ちの途中で奪われたとき（3つ目の画面が来た）は、前の画面の「終わった」（または待ちの時間切れ）を待ってから進む。先に自分の「終わった」を送ると、3つ目の画面が、前の画面の片付けの書き込みと重なって始まってしまう。
3. `audio.stop()`。
4. React の根を `unmount()` する（main.tsx が渡した片付けの関数）。各画面の後片付けが走る: おえかきは `saver.flush()`、4歳などのモードは回の終わりの時刻を書く。
5. **終わっていない保存が全部終わるまで待つ**（`src/core/pendingWrites.ts` の `waitPendingWrites()`）。おえかきの自動保存（`src/drawing/autosave.ts`）の書き込みの列は、すべてここに登録されている。画像（PNG）づくりが遅い端末では、書き込みの途中で窓を閉じて絵を切ってしまうため、固定の時間だけ待つ作りにはしない。
6. 0.3 秒待つ（送りっぱなしの書き込みが終わるのを待つ）。
7. `{t:'retired', from:<自分のID>}` を送る（新しい画面はこれを待ってから IndexedDB を開く）。
8. `window.close()`。
9. 0.3 秒たっても閉じていなければ `location.replace('./?retired=1')`（履歴を増やさない置き換え）。文書ごと入れ替わるので、途中の教材の取得・タイマー・音・IndexedDB の接続はすべて止まる。

- 後片付け（3〜6）は最大 4 秒で打ち切る（固まっても 7 へ進む）。打ち切ったときは、保存の途中で書き込みが切れることがある（8.5）。
- 教材パックの取得の途中だった場合、その取得は止まる。新しい画面の起動画面が既定パックの自動取得を始める（今の動き）。保護者が「きょうざい」で取っていたほかのパックは、もう一度「取得する」を押す（README の「困ったとき」に書いた）。

#### 2.3.4 画面の移動の履歴は変えない（D3 を採らなかった理由）

- `window.close()` が効くのは「スクリプトが開いた窓」か「**履歴が1件**の窓」だけ（Chromium の `DOMWindow::Close` は `BackForwardLength() > 1` なら閉じない。Firefox の `IsScriptClosable` も履歴 1 件。付録 B）。`--app` 窓も、外から開いた Firefox のタブも、開いた直後は履歴 1 件。
- アプリは `location.hash = hash` で画面を移るので、少し遊んだ画面は履歴が2件以上になり、自分では閉じられない。
- 設計の案は、画面の移動をすべて `replaceState` にして、いつも閉じられるようにすることだった。**採らなかった。** ブラウザの「戻る」と、おえかきの「新しい紙のあと、もどると前の作品が開く」を失う損が大きいため。`router.ts`・`router.test.ts`・`DrawingScreen.tsx` の `pushState`・`e2e/drawing.spec.ts` は変えていない。要件 OP-08 も作らない。
- 代わりに、**前の画面が自分を閉じられないとき**は、`./?retired=1` に置き換えて「べつの まどで ひらいています」だけを出す（2.3.3 の 9、2.3.5）。新しい画面は開いた直後で前にあるので、子供が見るのは新しい画面になる。
- 引き下がった窓が、使っている窓が閉じられたあとも残り続けることのないよう、鍵が空いたら自分で起動画面に戻る見張りを足した（2.3.5）。

#### 2.3.5 引き下がった画面（`src/app/RetiredScreen.tsx`）

- 出るとき: `?retired=1` で開かれたとき、または「戻る」「進む」の読み込みで生きている画面がいたとき。Service Worker は `?` を無視して `index.html` を返す（`sw.ts`）ので、オフラインでも出る。
- 中身（DESINGN.md 25 章）: 絵（おうち）＋大きな文字「べつの まどで ひらいています」（子供向け）＋小さな字「（保護者の方へ）まなびのにわは、ほかの窓で開いています。この窓は閉じてかまいません。」＋保護者向けの小さなボタン［この まどで ひらく］（`location.replace('./')`。押すと、この窓が引き継いで、ほかの窓が引き下がる）。
- **鍵が空いたら自分で戻る**: 2 秒おきに `navigator.locks.query()` で鍵 `manabi-no-niwa:main` の持ち主を見る（画面が見えるようになったときも見る。ただし前の調べから 1.5 秒たたないうちは見ない）。「空いている」が続けて2回出たら、`location.replace('./')` で自分で始め直す（`takeover:false` のふつうの起動）。調べられないとき（`query` が無い・失敗）は「空いた」と見なさない。2つの引き下がった窓が同時に戻っても、先に鍵を取った方が残り、遅れた方が奪って、先の方が引き下がるので、1つに落ち着く。
- 音を出さない。Service Worker の登録・IndexedDB・教材の取得をしない。題名は「とじた がめん（まなびのにわ）」。
- `data-testid`: `instance-retired`、ボタン `instance-reopen`。
- `RetiredScreen.tsx` は、絵・CSS・`src/core/instance/instance.ts`（鍵の見張りだけ使う）以外を読み込まない（試験で確かめている）。

#### 2.3.6 記録の書き込みが二重にならないこと

- 同じブラウザでは、書く画面（`primary`）はいつも1つ。進み具合・つづき・お気に入りの上書き、設定の古さ、プロフィール削除のあとの書き込み、スキーマを上げる更新での記録の取りこぼし、教材パックの取り合い・キャッシュの消し合い、音の重なり、時間の二重の数え、といった困りごとは、同じブラウザの中では起きなくなる。
- 引き継ぎのとき、新しい画面は前の画面の `{t:'retired'}`（片付けの書き込みが終わったあと）を待ってから IndexedDB を開き、教材の照合（`reconcilePacks`）・自動取得を始める（`startOffline()` と描画が `claimInstance()` のあとにあるため）。
- 返事の無い（凍結した）画面から奪ったときは待たない。凍結した画面は動けないので書かない。戻ったときは、まず奪われたことを処理して引き下がる（間に IndexedDB の結果の処理が1つ走ることはありうる。おえかきの `updatedAt` の比べは残す）。
- 既存の守り（おえかきの「べつの がめんで かいています」、IndexedDB の versionchange・`blocked` の文）は消さない。別のブラウザ同士・Web Locks の無いブラウザの保険として残す。

#### 2.3.7 例外

| 場合 | 動き |
|---|---|
| Web Locks が無い（Chromium 68 以前・Firefox 95 以前） | `unsupported`。今までどおり（道 A だけが働く） |
| 試験の旗 `sessionStorage['mnw:test:multiWindow']='1'` | `unsupported`。2つのタブを同時に使う既存の e2e（おえかきの2つのタブ、Service Worker の旧タブ・新タブ）のためだけ。製品では使わない。localStorage ではなく sessionStorage から読む（家庭のパソコンに消し忘れが残り続けて、守りが黙って切れないように） |
| ほかのページの枠（iframe）の中 | `unsupported`。鍵を奪わず、返事もしない。枠を使って本物の窓を追い出すことはできない |
| ほかのサイトのページが、同じブラウザで `127.0.0.1:8765` を開く（ページの移動・新しい窓・新しいタブ） | **残るリスク（2.1.0 では直さない。3回目の点検 app-1）。** 開かれ方はふつうの読み込みなので、生きている画面がいれば鍵を奪われ（2.3.1 の 5）、使っている窓（子供の窓）が引き下がる。窓を閉じられなければ「べつの まどで ひらいています」に替わる。記録は残る（失うのは、前の画面のいまの場面だけ）。［この まどで ひらく］を押すか、アイコンを押し直すと戻る。ほかのサイトが得るものは無い（窓が入れ替わるだけ）。`referrer`・`history.length` では見分けられず（`noreferrer` ですり抜けられる）、守りにならない。直し方の候補（起動の印）は 8.6、残るリスクとしては 8.5 |
| 別のブラウザ（Firefox と Brave）・別のプロファイル・プライベート窓 | お互いに見えない（鍵はプロファイルとオリジンごと）。記録も別々なので範囲外（README の「ブラウザを変えると記録は別々」） |
| 開発サーバー（`127.0.0.1:5173` など） | オリジンが違うので本番とは別。開発中も守りは働く（旗で止められる） |


#### 2.3.8 更新の仕組みとの関係

- 更新の仕組みの `startUpdater()` は `startOffline()` の中から呼ばれる → `primary` の画面でだけ動く。
- 更新の仕組みの「読み込み直し」（`applyUpdate()` → `location.reload()`）は 2.3.1 の 4〜5 で、0.4 秒だけ待って「返事なし」になり、`takeover:false` で始まる（全画面にはしない）。
- 「新しい版は窓を全部閉じるまで切り替わらない」（README の「新しい版に更新するとき」）は、窓が1つになるので「窓を閉じて開き直せば切り替わる」に近づく（文書はそのまま正しい）。
- 引き継ぎで前の画面の更新の仕組みの流れ（画面の側）は止まるが、配信の側の更新の作業は続く。新しい画面の `startUpdater()` が「配信が作業中」から続ける（updater-design.md 6.4）。

### 2.4 (d) 全画面の扱い

#### 2.4.1 最初の起動は全画面にしない（D5）

- 依頼は「二重起動しようとしたら」だけ。
- 最初の起動は保護者の準備（README の手順 5〜7: 保護者画面・教材の取得）にも使う。全画面だと窓の閉じるボタンもタスクバーも隠れて、手順の説明と合わなくなる。
- 道 B と同じく、ページの側ではタップ無しに全画面にできない。起動スクリプトで全画面にすると、道 A と道 B で入り方がそろわない。
- 将来「ひらくときから全画面」を保護者の設定で選べるようにするなら: X11 で見えるときは `manabi.sh` が `wait` のあとに全画面を送り、見えないときは「はじめる」で入る。今回は作らない。

#### 2.4.2 道 A の全画面（ブラウザの全画面）

- 起動スクリプトが送る全画面は、ブラウザの全画面（F11 と同じ）になる（付録 A）。**F11 で戻る。Esc では戻らない**。
- 全画面のあいだは窓の閉じるボタンとタスクバーが見えない。やめるときは F11（ノートパソコンでは Fn＋F11 のことがある）で戻してから閉じる。Alt＋F4 でも閉じられる。
- キーボードの無いタッチだけの使い方: 3本指で上へなで上げる（またはスーパーキー）とアクティビティの画面になり、窓を選ぶ・閉じる（×）ことができる【要実機】。
- ブラウザが「全画面を終了するには F11」の小さな知らせを数秒出す（ブラウザの機能。消せない）。

#### 2.4.3 道 B の全画面（「はじめる」で）

- `takeover:true` の画面だけ、起動画面の「はじめる」を押したときに `document.documentElement.requestFullscreen()` を呼ぶ（`StartScreen.tsx` の `begin` の**最初の await より前**。タップのユーザー操作の中で呼ぶため）。失敗は無視する。1回だけ（2回目の「はじめる」では呼ばない）。
- これはページの全画面（保護者画面のボタンと同じ種類）。Esc・F11・保護者画面の「全画面をやめる」で戻る。
- `takeover:false`（ふつうの起動・読み込み直し）では呼ばない。

#### 2.4.4 保護者画面「せってい」の全画面の節（`SettingsTab.tsx` の `FullscreenSection`）

判定は小さな関数（`src/ui/fullscreen.ts`: `fullscreenMode()`・`isPageFullscreen()`・`isWindowFullscreen()`・`requestAppFullscreen()`・`requestStartFullscreen()`）にまとめ、起動画面（`StartScreen.tsx`）と `SettingsTab.tsx` で使う。

| いまの状態 | 表示 |
|---|---|
| ページの全画面（`document.fullscreenElement` がある） | ボタン［全画面をやめる］ |
| 窓の全画面（ページの全画面ではないが、`matchMedia('(display-mode: fullscreen)')` が真、または `innerWidth`・`innerHeight` が `screen` の幅・高さと同じ） | ボタンを出さずに文だけ。「いまは全画面で表示しています。やめるには F11 キーを押してください。ノートパソコンでは、Fn キーを押しながら F11 キーを押すことがあります。」 |
| どちらでもない | ボタン［全画面にする］ |

- ボタンがあるときの注記: 「まなびのにわを開いているときにアイコンをもう一度押すと、その窓を前に出して全画面にします。前に出せないときは、新しい窓で開き直して、「はじめる」を押したときに全画面にします。F11 キーを押すと、いつでも元に戻ります。このボタンで全画面にしたときは、Esc キーでも戻ります。」
- ページの全画面の出入りは `fullscreenchange`、窓の全画面の出入り（F11 など）は `resize` で見る。
- 【要実機】Chromium の `--app` 窓・Firefox で、ブラウザの全画面のとき `display-mode: fullscreen` が真になるか（ならなくても大きさの比べで分かる）。


#### 2.4.5 子供に分かりやすいか

- 道 A: 窓が前に出て、そのまま画面いっぱいになるだけ。音・確認の画面・動きの演出は足さない。遊んでいた画面が続く。
- 道 B: 前の窓が消えて、見慣れた起動画面が出る。「はじめる」で画面いっぱいになる。
- 間違って F11・Esc で戻っても害は無い。次にアイコンを押せばまた全画面になる。「おうち」ボタン（CX-02）は全画面でも同じ場所にある。
- 子供の画面に、二重起動についての知らせ・ボタンは出さない（2.3.5 の画面は、閉じきれなかった窓にだけ出る）。

## 7. 残るリスク・決めなかったこと

- **③（Wayland ネイティブで先に動いていたブラウザ）では前の画面の続きを失う。** 記録は残る。ブラウザを全部閉じて開き直せば、次から②になる。
- `--ozone-platform=x11` の副作用（保護者のふつうの Brave の窓も XWayland になる。X11 の窓は同じ画面のほかのアプリから入力や画面を読み取られうる。分数スケーリングの判定が外れるとぼやける）。`MANABI_OZONE=native` で止められる。
- Brave の今後の版で `--app` 窓の res_name・題名の付け方が変わると道 A が効かなくなる（そのときは道 B に落ちるだけで、窓が2つ残ることは無い）。
- 2種類のブラウザで同時に開くことは止めない（2.2.2 の形で将来足せる）。
- 「ひらくときから全画面」の設定は作らない（2.4.1）。
- `.desktop` の `StartupNotify`・`StartupWMClass` は変えない（2.1.3）。変えると入れ直しが要り、Shell が全画面なしで窓を前に出す道ができる。
- 画面の移動の履歴を変えないため、画面を移したあとの前の窓は自分を閉じられず、「べつの まどで ひらいています」の窓が残る。使っている窓が閉じられれば自分で戻る（2.3.5）。
- ほかのサイトのページが同じブラウザで `127.0.0.1:8765` を開くと、使っている窓が引き下がる（2.3.7・8.5）。記録は残り、［この まどで ひらく］かアイコンの押し直しで戻る。直し方の候補は 8.6。
- そのほかの残るリスクは 8.5。

- 点検（攻撃の目）を「起動の側」と「アプリの側」の2つで行い、高い指摘は無く、中の指摘が 2 件あった。どちらも直した（8.4）。点検で使った試験の台本（偽の X・偽の相手・1 バイトずつ返す相手・リンクの置き換え・形の違う知らせ・遅い PNG）で、指摘のとおりに再現することを確かめてから直した。
- シェルへの注入（環境変数に `$( )`・バッククォート・`;` を入れる）、引数への注入、鍵の fd が子に渡らないこと、期限がどれも有限であること、ctypes の構造体が Xlib の並び（96・64・192 バイト）と同じであることを点検で確かめた。

### 8.2 確かめていないこと

- **Zorin の実機での前面化と全画面**（X11 と XWayland・Mutter。最小化中・別のワークスペース・Zorin メニューから開いたとき）。6 章と device-checklist に項目を集めた。
- 本物の `flock`（Git Bash に無く、WSL も無い。本物の `flock` の試験は Windows では飛ぶ）、本物のシンボリックリンク（Windows では権限が無く作れない。ハードリンクで同じ「たどって書く」道を確かめた）。
- 時間切れの見張り（`faulthandler`）が、本物の libX11 の呼び出しの中で固まったときに効くこと（Windows の `time.sleep` と、SIGALRM を止めた形で確かめた。本物の固まった X サーバーでは未確認）。親が SIGALRM を無視にして起動した場合の試験は、Linux でだけ動く（Windows では飛ぶ）。
- Chromium 系（Brave）で開く端末の実機で、窓が前に出ること、Firefox の窓が前に出ないこと（偽の X と偽の `manabi.sh` の上でだけ確かめた）。
- Chrome のアドレス欄の先読み（prerender）で `127.0.0.1:8765` が先に読み込まれたとき、Web Locks の要求が有効になるまで待たされるか。待たされなければ、保護者がアドレス欄に打つだけで子供の窓が引き下がりうる（仕様では待たされるはず。未確認。3回目の点検）。
- `-I` を Python 3.10 で動かすこと（3.12 で確かめた。3.4 以降は同じ仕様）。
- Brave の `--app` 窓の履歴の数と `window.close()` の効き方、2つの `--app` 窓が同じブラウザのプロセスの手元を分け合うか、Firefox がセッションを戻すときに `?retired=1` のタブも戻すか。
- Zorin の実機での `toBlob` の速さ（保存を待つ上限 4 秒で足りるかは、これで決まる）。
- Mutter の挙動はソースを読んで判断した。実機では動かしていない。

### 8.5 残るリスク（8.4 で直さなかったものを含む）

- 保存が上限（4 秒）をこえて終わらないとき、窓を閉じて書き込みが切れる。失うのは、前の画面のいまの場面と、おえかきの最後の描き足し。記録は1問ごと・回の終わりに書いている。
- 手元が 1 秒以上ふさがった画面は、凍結した画面と見なされ、新しい画面が保存を待たずに始まる。そのときは「はじめる」でも全画面にならない。
- ［この まどで ひらく］で引き継ぐと、「はじめる」で全画面になる（引き継ぎのため）。
- bfcache から戻った画面は `location.reload()` で読み込み直す。読み込み直しとして扱われるので、使っている窓があれば、鍵を奪う。
- `mnwwindow.py` が 500 行ちょうどで、行数の試験の上限と同じ（余裕が 0 行）。次に足すときは、まとめ方を詰めるか、`write_log` と `X11Backend` を別のファイルへ分ける。
- 鍵を持たずに動いたとき（`flock` が無い環境）は、`launch.log` の行が同時の書き込みで消えることがある。10 秒の打ち切りが書き込み中に来ると、`.launch.log.*` の一時のファイルが残ることがある。
- 弱い一致: 別のポートや別のホストの `--app` 窓（開発者だけが起こす）は、前に出されうる。Firefox で開く端末では、Firefox で題名がちょうど「まなびのにわ」の別のサイトのタブも、前に出されうる（Chromium 系で開く端末では、Firefox の窓は候補にしない。8.6）。`--browser firefox` のときも、Chromium 系の弱い一致（末尾の付かない題名のアプリ窓）は候補に残る。`firefox` のときに Chromium 系を外して対称にするかは、次の版の判断にした。
- Firefox の裏のタブ・Wayland のネイティブの窓は、外から見つけられない（道 B になる）。
- **ほかのサイトのページが、同じブラウザで `127.0.0.1:8765` を開くと、使っている窓（子供の窓）が引き下がることがある**（3回目の点検 app-1。2.3.7）。新しい画面は、ふつうの読み込み（`back_forward` でも `reload` でもない）で、生きている画面がいるので鍵を奪い、前の画面は「べつの まどで ひらいています」に替わる（引き継ぎの作りで入った道）。記録は残る（失うのは前の画面のいまの場面だけ）。［この まどで ひらく］を押すか、アイコンを押し直すと戻る。ほかのサイトが得るものは無い。`referrer` や `history.length` で見分ける方法は、`noreferrer` などですり抜けられるので守りにならず、採らない。2.1.0 では文書に書くだけにして、仕組みの直し（起動の印。8.6）は次の版の候補にした。

## 付録 A. OS まわりの調べ（要点）

調べた日は 2026-11-06。Windows 上で Web の文書とソースを読んだだけで、Zorin の実機では試していない。

1. **Zorin 17・18 とも既定の画面は Wayland**。GPU や設定で Xorg になる機種がある（NVIDIA の専用ドライバ、`nomodeset`、ハイブリッド GPU のノートなど。16 から更新した端末は Xorg のまま残りうる）。両方を前提にする。判定は実行時に `XDG_SESSION_TYPE`。
2. **新しく入れた Zorin 17.3 以降・18 の既定のブラウザは Brave**（APT 版）。Firefox は入っていない（17.2 以前から更新した端末は Firefox のまま）。Chromium は最初から入っていない。→ ほとんどの端末で動くのは `brave-browser --app=URL`。README の「最初から入っている Firefox」を直した。
3. **`wmctrl`・`xdotool` は最初から入っていない**。使えるのは python3（17 は 3.10、18 は 3.12）＋ ctypes で `libX11.so.6`、`xprop`・`xwininfo`（読むだけ）、`gdbus`、`flock`。
4. **X11 の窓なら、外から前面＋全画面にできる**。EWMH の `_NET_ACTIVE_WINDOW`（source=2）と `_NET_WM_STATE`（ADD、`_NET_WM_STATE_FULLSCREEN`）を root 窓へ送る。Mutter（GNOME）43.8・46.2 のソースを読んだ結果:
   - 時刻を「いま取ったサーバー時刻」（0 バイト追記の PropertyNotify で得る）にすると、フォーカスを奪う防ぎ（focus stealing prevention）を通り、別のワークスペースにあっても切り替えて前面に出る。
   - 時刻 0 でも前面に出る（警告がログに出る）。古い時刻だと前面に出ず、「準備ができました」の通知になる。
   - GNOME Shell がつかみ中（オーバービュー・メニュー・Alt+Tab）は黙って無視されるので、確かめてやり直す。
   - Chromium は窓マネージャーが付けた全画面を、自分の全画面（F11 相当）として扱う。
5. **Wayland ネイティブの窓は、外のプロセスから前面に出せない**（xdg-activation は自分の窓にしか使えない。`org.gnome.Shell.Eval` は unsafe mode のときだけ。Shell の D-Bus は許可リスト制）。GNOME Shell 拡張は、設定の変更と再ログインが要り、「端末の設定を変えない」に反するので使わない。
6. **Chromium 140 以降は Wayland セッションで既定で Wayland ネイティブ**。`--ozone-platform=x11` を付けると XWayland の窓になり、4 の方法が使える。ただし効くのは、その起動でブラウザのプロセスが新しく立ち上がるときだけ（すでに動いていれば、その中に窓ができて指定は無視される）。プロファイル・オリジンは変わらない。
7. **同じ `--app=URL` をもう一度起動すると、Chromium は既存のプロセスに引き渡して、新しいアプリ窓をもう 1 枚開く**。`--start-fullscreen`・`--kiosk`・`--class`・`--ozone-platform` は、最初に立ち上がったプロセスのコマンドラインしか見ない。最初の起動に `--start-fullscreen` を付けると、そのプロセスで後から開くふつうの窓まで全画面になる。→ 使わない。
8. **`--app=URL` の窓の `WM_CLASS` の res_name は URL のホスト（`127.0.0.1`）になる**（ポート・ハッシュは入らない）。これは引き渡された起動でも付く。【要実機】
9. **PWA の `launch_handler: focus-existing`** は、インストール済みの PWA を `--app-id` で起動したときだけ効く。インストールは人の操作か root のポリシーが要るので、使えない。Firefox は非対応。
10. 起動の直列化は `flock`（util-linux）。鍵のファイルは `$XDG_RUNTIME_DIR`（ログアウトで消える）か `$STATE_DIR`。

## 付録 B. ブラウザまわりの調べ（要点）

調べた日は 2026-11-06。「仕様」「互換表」「コード」「推定」の別は、元の調べでは項目ごとに付けた。実機では確かめていない。

| 問い | 答え |
|---|---|
| 2つ目のページを見つける | **Web Locks API がいちばん確実**（Chromium 69〜、Firefox 96〜）。1つ目が鍵を持ち続け、2つ目は `ifAvailable: true` で取れなければ「2つ目」と分かる。ページが閉じる・落ちると自動で解放される。1つ目への知らせは BroadcastChannel |
| 2つ目が自分を閉じる | **閉じられる**。新しく開いた窓やタブは履歴が1件なので「スクリプトから閉じてよい窓」に当たる。ただし画面の移動で履歴が増える前に |
| 1つ目を閉じる | 履歴が2件以上だと、`window.close()` は無視される（どちらのブラウザでも） |
| 1つ目が自分の窓を前面に出す | **ページからはできない**。Chromium は 2012 年以降許さない。Firefox は `dom.disable_window_flip = true`（既定）。Service Worker の `WindowClient.focus()` も、通知をクリックしたときだけ |
| 1つ目を全画面にする | **自動ではできない**。`requestFullscreen()` は、その窓の中でのユーザー操作が必須。別の窓での操作は引き継がれない。例外は管理者のポリシーだけ。→ 前面に来たあと、最初のタップで全画面にする |
| PWA として入れた場合 | `display: "fullscreen"` はデスクトップの Chromium では standalone 扱い。`launch_handler` は `--app=URL` の起動では効かない |

Web Locks の性質: 範囲は「ストレージの区画」（ほぼオリジン）ごと。同じブラウザの同じプロファイルのタブ・窓・ワーカーで共有される。別のプロファイル・プライベート窓は別扱い。別のブラウザ同士（Firefox と Brave）は互いに見えない。`ifAvailable: true` はすぐ取れなければコールバックが `null` で呼ばれる。`steal: true` は持っている相手から奪い、奪われた側の Promise が AbortError になる（相手のコードが止まるわけではない）。安全なコンテキストでのみ使える（`http://127.0.0.1` は信頼できるオリジン）。ほぼ同時の2つの起動でも、鍵の割り当ては1か所で順に決まる。
