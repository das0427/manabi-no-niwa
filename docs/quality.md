# 品質の確かめ方（quality.md）

このアプリで、何をどう確かめたか、その数、確かめていないことを書きます。守っている約束は2つです。実際の数を書くこと。確かめていないことを書くこと。

- 対象は 2.1.0 です。テストや検査の数は、公開の前の確認（2026-11-28）の結果です。
- 実機（Zorin OS）と子供での確認は、まだしていません。学習の効果も検証していません。
- 検査の多くは機械が測ったものです。人が画面を見たり音を聞いたりして確かめたものではありません。AI が人の代わりに読んだものも、実際の保護者や子供の反応ではありません（[ai-roles.md](ai-roles.md)）。

#### テストの作りの直し（次の版に向けて。2026-11-28）
offline・packs・serve の E2E の写し方と組み立て方を直し、音声入りのビルドで流しました。この開発機（Windows 11）で測った値です。E2E は一時の設定（127.0.0.1:5290 の vite preview・1ワーカー・組み立て済みの dist）で流しました。

直したこと

- つないだフォルダの中を消す・書く操作はエラーにします。つなぎ先の dist が変わるためです。
- 見本パック入りの組み立ては、public を写さずに行い、音声はつないで入れます。テストの時間の外（beforeAll）で、ワーカーごとに一度だけ行います。

- offline の updateUntil は、まず状態を読み、条件を満たしていれば update() を呼ばないようにしました。前は、失敗を見つけた回の update() が失敗した版の install をやり直させ、その作りかけのキャッシュを直後の確かめが見て落ちていました（音声入りでだけ起きます。やり直しが約40秒続くためです）。

結果: 音声入りの dist・Chromium
- serve.spec の11件はすべて合格しました。
- 全件の保存が1回の試験は、取得の失敗なしで合格しました。offline の「準備完了 → 配信を停止」・ブラウザを閉じて開き直す試験・全9モード・CSP の試験と、packs の (1)(2)(6) と (4) です。
- 全件の保存を2〜3回行う試験は、通ったり落ちたりします。offline の更新の試験（3回）は合格しましたが、通信の記録に ERR_ADDRESS_IN_USE が138件あり、取得の失敗と install のやり直しを経て通っていました。packs の (3)(5)（3回）と「packs.json に無いパック」（2回）は、単独の1回目は合格し、通信の記録を取った2回目は落ちました（ERR_ADDRESS_IN_USE が431件・41件）。offline と続けて流した回も落ちました。offline の「新版の準備に失敗しても」（2回）は、単独では合格しましたが（39.5秒）、続けて流すと落ちました。
- 原因は、Windows の開発機の制約と見ています。serve.py は要求ごとに接続を閉じ、全件の保存1回で約1万600の接続を使います。この PC の一時ポートは 16,384 個です。閉じた接続は TIME_WAIT として残るので（packs を単独で流したとき最大 13,139）、残るうちに次の全件の保存を始めるとポートが尽き、取得が失敗します。
- Zorin（Linux）の本番では、1回の更新で全件の保存は1回です。Linux は loopback の TIME_WAIT を使い回せるので、当たらない見込みです（確かめていません）。

結果: 音声入りの dist・Firefox
- 全件の保存が1回の試験も落ちました。offline の「準備完了 → 配信を停止」と、packs の (1)(2)(6) です。準備の待ち（105.8秒）を超え、「オフラインの準備に失敗しました。保護者画面を見てください。」が出ていました。
- 原因はアプリの問題です。Firefox は Service Worker を、最後の出来事の30秒後、waitUntil で延ばしても60秒までで止めます（正式版の既定の設定）。install の途中でも止まります。音声入りの全件の保存は Firefox で約58秒かかり（寿命の設定を延ばして測ると 57.7秒）、延ばさないと3回とも途中（8,148・9,591・10,267件）で止まりました。
- Zorin 17.2 以前から更新したパソコンは Firefox で開きます。そのパソコンでは、2.1.0 の配布の初回の準備が終わらず、オフラインで使えない見込みです（確かめていません）。
- テストでは寿命を延ばしていません。延ばすと、本番と違う形で通ってしまうためです。直しは別の作業です（handover.md B）。

結果: 音声を置かないビルド（dist 2,424ファイル・コア 2,375）
- 組み立ては45秒でした。
- Chromium は serve 11件・offline 6件・packs 4件の計21件がすべて合格しました（3.7分・1ワーカー）。
- Firefox は offline 6件・packs 4件の計10件がすべて合格しました（6.6分）。serve.spec は Chromium だけです。
- 2.1.0 の記録では、Chromium の packs が1回目に1件、最初の準備の待ち（60秒）で落ちていました。今回は落ちませんでした（流したのは1回だけです）。

依頼から外れた点（待ちの直し）
- 依頼は、テストの制限を延ばして通すのではなく、写し方と組み立て方を直すことでした。直したあとも、音声入りでは、アプリ（Service Worker）が全件を事前保存する時間に待ちが足りませんでした。写す時間ではなく、アプリが実データで行う仕事の時間で、今回はじめて測りました。
- 全件の事前保存は、音声入りのコア（10,577ファイル・約190MB）で、Chromium が 40.4秒、Firefox が 57.7秒でした。待ちは、offline.spec が30秒、packs.spec が60秒で、音声を置かないビルドに合わせた値でした。
- 待ちを1ファイル10ミリ秒で計算し、下限を今の値にしました。テストの制限には、全件の保存の回数ぶんを足します。音声入りでは1回の待ちが 105.8秒です。音声を置かないビルドでは、待ちもテストの制限も今と同じ値です。

## 検査の限界
- 機械の検査は、測れるものだけを見ます。字がはみ出すかは測れても、読みやすいか、子供に分かるかは測れません。
- 検査を作った AI と、直した AI は、同じ系統です。検査の見落としは、検査の検査（probe）と、点検での再現で減らしましたが、無くなってはいません。
- 検査の結果は、検査を実行した時点のコードのものです。公開のあとに変わった所は、確かめ直しが要ります。
- 判定役の比較は、新しい文が読みやすいかを AI が選んだ結果です。事実の正しさは別に確かめています。
